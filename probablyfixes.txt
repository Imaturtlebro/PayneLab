Yes — I definitely see useful leg-related changes to try from these five files. I would **not** say “nothing useful” here.

The legs are being driven by several systems at once:

- `PayneLabLegPoses` writing `ConfigurableJoint.targetRotation`
- `PayneLabJointControl` changing joint springs/dampers/forces
- `PayneLabObstacleClearance` injecting extra knee lift
- `PayneLabStateMachine` switching states that instantly change pose/drive goals
- `PayneLabStabilizer` adding body torque
- possible friction material swaps on the leg/pelvis colliders

When one of those is slightly wrong, the legs can look “crazy” because the joint drives amplify the error. Ragdoll being more stable makes sense: in ragdoll you drop to weak drives and mostly neutral targets, so the bad targeting/conversion has less authority.

Below are the biggest suspects and the changes I would make first.

---

# 1. Biggest suspect: `ConfigurableJoint.targetRotation` conversion in `PayneLabLegPoses`

This function is the most likely source of violent leg behavior:

```csharp
private Quaternion ComputeJointTargetRotation(ConfigurableJoint joint, Quaternion desiredPose)
{
    if (joint == null) return Quaternion.identity;

    Quaternion inv = Quaternion.Inverse(desiredPose);

    Vector3 right = joint.axis;
    Vector3 forward = Vector3.Cross(joint.axis, joint.secondaryAxis);

    if (forward.sqrMagnitude < 0.0001f)
    {
        return inv;
    }

    forward.Normalize();

    Vector3 up = Vector3.Cross(forward, right).normalized;
    Quaternion jointSpace = Quaternion.LookRotation(forward, up);

    return Quaternion.Inverse(jointSpace) * inv * jointSpace;
}
```

This is doing a nontrivial conversion from a simple “bend pose” into joint-axis space. If the avatar’s hip/knee joint axes are not exactly what this expects, the joint can receive a target that twists the leg instead of bending it cleanly. With high joint springs, that becomes explosive.

## Why this matters

Your pose targets are mostly simple X-axis bends:

```csharp
LeftKneeTarget = Quaternion.Euler(90f + kneeClearance, 0f, 0f);
```

But Unity/PhysX `ConfigurableJoint` orientation targets are very easy to get wrong, especially across different BONELAB avatars. If the mapping is off by one axis, the knee/hip can:

- bend backward
- twist sideways
- jitter violently
- fight the stabilizer
- invert behavior depending on avatar
- look fine on one rig and crazy on another

## Quick diagnostic

Temporarily disable the joint-space conversion and see if the legs calm down:

```csharp
private Quaternion ComputeJointTargetRotation(ConfigurableJoint joint, Quaternion desiredPose)
{
    if (joint == null) return Quaternion.identity;

    // TEMP diagnostic: bypass complex joint-space conversion
    return Quaternion.Inverse(desiredPose);
}
```

Or try the opposite:

```csharp
return desiredPose;
```

If one of those immediately makes the legs less insane, then the current `jointSpace` conversion is the main problem.

Long-term, I would move away from this generic conversion and instead store per-joint calibration:

- initial local rotation
- primary bend axis
- sign for left/right
- min/max angle clamp

That will be much more stable than trying to infer everything from `joint.axis` and `joint.secondaryAxis` every frame.

# 2. Pose slew rate is too high

This is also suspicious:

```csharp
private const float MaxPoseSlewRate = 420f; // degrees per second
```

420 degrees/sec is very fast for physics-driven ragdoll joints, especially knees.

For example, standing knee target:

```csharp
LeftKneeTarget = Quaternion.Euler(5f, 0f, 0f);
```

Knee slide target:

```csharp
LeftKneeTarget = Quaternion.Euler(90f + kneeClearance, 0f, 0f);
```

That is an ~85 degree change. At 420 deg/sec, it can arrive in about 0.2 seconds. With strong knee springs, that can spike the solver.

## Change

Split hip/knee slew rates and lower them:

```csharp
private const float MaxHipSlewRate = 180f;
private const float MaxKneeSlewRate = 140f;
```

Then:

```csharp
float hipStep = MaxHipSlewRate * Time.fixedDeltaTime;
float kneeStep = MaxKneeSlewRate * Time.fixedDeltaTime;

_curLeftHip = Quaternion.RotateTowards(_curLeftHip, LeftHipTarget, hipStep);
_curRightHip = Quaternion.RotateTowards(_curRightHip, RightHipTarget, hipStep);
_curLeftKnee = Quaternion.RotateTowards(_curLeftKnee, LeftKneeTarget, kneeStep);
_curRightKnee = Quaternion.RotateTowards(_curRightKnee, RightKneeTarget, kneeStep);
```

This alone may reduce the “legs go crazy on state change” behavior.

# 3. `ObstacleClearance` is currently too aggressive and can leave stale knee lift

This part is active during:

```csharp
StuntState.KneeSlide
StuntState.ButtSlide
StuntState.DiveProne
```

But the knee clearance value is only used in:

```csharp

```

And it can push the knee target up by 25 degrees:

```csharp

```

That is a lot.

Also, if speed drops below 0.5, it returns early without decaying the offsets:

```csharp

```

So if you were sliding fast, detected an obstacle, then slowed down, the knee can remain lifted at a high angle for no reason.

## Problems here

- `25f` degrees is too much for a reactive knee lift.
- It can false-positive on floor lips/ramps/collider seams.
- It does not check hit normal.
- It remains active during `DiveProne`, even though `DiveProne` does not use the value.
- Slow slides keep stale clearance.
- `GetFootClearance()` is not used by `PayneLabLegPoses`, so foot clearance is just accumulating for nothing.

```csharp
    RightKneeTarget = Quaternion.Euler(90f + kneeClearance, 0f, 0f);
```

If the legs get calmer during slides, obstacle clearance was contributing.

# 4. Joint drive smoothing is not actually smoothing over time

In `PayneLabJointControl`, you have this:

```csharp
public void OnStateChanged(StuntState from, StuntState to)
{
    if (!_drivesCached)
        CacheJointDrives();

    ApplyStateDriveParams(to);
}
```

And inside `ApplyStateDriveParams` you do:

```csharp
float rate = Mathf.Clamp(Time.fixedDeltaTime * DriveSmoothingRate, 0f, 1f);

_hipSpringNow = Mathf.Lerp(_hipSpringNow, hipSpring * mult, rate);
_hipDamperNow = Mathf.Lerp(_hipDamperNow, hipDamper * mult, rate);
...
```

But `ApplyStateDriveParams` is only called on state change, not every tick.

That means the smoothing only takes one small step when the state changes, then stops. It does not continuously smooth toward the target values.

So state switches still cause hard spring/damper jumps.

## Fix

Call `ApplyStateDriveParams(_mod.CurrentState)` every fixed update when not in full ragdoll/full IK.

Example:

```csharp
public void Tick()
{
    if (_mod.ActiveInput == InputMode.FullRagdoll)
    {
        ApplyFullBodyLimp();
        _limpApplied = true;
        return;
    }

    if (_limpApplied)
    {
        RestoreFullBodyDrives();
        _limpApplied = false;
    }

    // If FullIK means the game's IK should own the legs, do not fight it.
    if (_mod.ActiveInput == InputMode.FullIK)
        return;

    // Continuously smooth drive parameters
    ApplyStateDriveParams(_mod.CurrentState);

    var rb = _mod.CachedPelvisRb;
    if (rb == null) return;

    bool isGrounded = _mod.StateMachine != null && _mod.StateMachine.IsGrounded();

    if (!isGrounded &&
        (_mod.CurrentState == StuntState.Aerial ||
         _mod.CurrentState == StuntState.Cannonball ||
         _mod.CurrentState == StuntState.DiveProne))
    {
        ApplyAerialTorque();
    }

    if (_mod.CurrentState == StuntState.GroundRoll ||
        _mod.CurrentState == StuntState.KneeSlide ||
        _mod.CurrentState == StuntState.ButtSlide ||
        _mod.CurrentState == StuntState.SideLying ||
        _mod.CurrentState == StuntState.DiveProne)
    {
        ApplyGroundRollTorque();
    }
}
```

This makes drive transitions much softer.

# 5. Right-stick yaw can make prone legs pump because of `GetProneTuckBlend`

This is especially relevant if you want omnidirectional diving/prone with right stick.

In `PayneLabLegPoses`:

```csharp
private float GetProneTuckBlend(float settleRate)
{
    ...
    float yawRate = Mathf.Abs(angVel.y);
    float target = Mathf.Clamp01((yawRate - 1.5f) / 3.0f);
    ...
}
```

The comment says:

```csharp
// Only actual rapid physical yawing tucks knees (Right Stick deflection is omitted
// so aiming and turning will never cause the knees to pump like bicycle pedals).
```

But if right stick torque is used to rotate the body, then right stick deflection **does** create physical yaw angular velocity. So this still causes knee tuck.

That means if you implement RS omnidirectional prone turning, the legs may pump because:

1. RS creates yaw torque.
2. Body angular velocity rises.
3. `GetProneTuckBlend` sees yaw rate.
4. Knees tuck.
5. Yaw slows.
6. Knees untuck.
7. Repeat.

That can look very janky.

## Fix

Disable prone tuck while right stick is active, or make it much harder to trigger.

Example:

```csharp
private float GetProneTuckBlend(float settleRate)
{
    var rb = _mod.CachedSpineRb ?? _mod.CachedPelvisRb;
    if (rb == null) return 0f;

    // If the player is actively using right stick control, do not let the
    // resulting angular velocity pump the knees.
    if (_mod.Input != null && _mod.Input.RightStick.sqrMagnitude > 0.04f)
    {
        _proneTuckBlend = Mathf.MoveTowards(
            _proneTuckBlend,
            0f,
            Time.fixedDeltaTime * settleRate
        );

        return _proneTuckBlend;
    }

    Vector3 angVel = rb.angularVelocity;
    if (!PayneLabUtils.IsFinite(angVel)) angVel = Vector3.zero;

    float yawRate = Mathf.Abs(angVel.y);

    // Raise threshold significantly
    float target = Mathf.Clamp01((yawRate - 3.0f) / 4.0f);

    float blend = _proneTuckBlend;
    float step = Time.fixedDeltaTime * settleRate;

    if (target > blend)
        _proneTuckBlend = Mathf.MoveTowards(blend, target, step * 1.5f);
    else
        _proneTuckBlend = Mathf.MoveTowards(blend, target, step);

    return _proneTuckBlend;
}
```

For stable prone aiming, I might disable prone tuck entirely at first:

```csharp
private float GetProneTuckBlend(float settleRate)
{
    return 0f;
}
```

Then add it back later if you really want it.

# 7. Aerial torque also brakes hard when right stick is released

This code:

```csharp
Vector3 desiredLocalAngVel = new Vector3(
    rs.y * _mod.AerialFlipTorque,
    0f,
    -rs.x * _mod.AerialFlipTorque
);

Vector3 currentLocalAngVel = rb.transform.InverseTransformDirection(rb.angularVelocity);
Vector3 error = desiredLocalAngVel - currentLocalAngVel;
Vector3 localTorque = Vector3.ClampMagnitude(error * AerialTorqueGain, MaxAerialAngularAccel);
```

When right stick is zero, desired angular velocity becomes zero. That means this becomes a strong angular brake.

That can be useful, but it can also snap the body and make the legs react violently.

Also:

```csharp
private const float MaxAerialAngularAccel = 300f;
```

That is quite high.

## Suggested change

Reduce the max accel and make stick-released damping softer.

For example:

```csharp
private const float AerialTorqueGain = 6f;
private const float MaxAerialAngularAccel = 120f;
```

And optionally only apply strong torque when the stick is actually deflected:

```csharp
private void ApplyAerialTorque()
{
    var rb = _mod.CachedPelvisRb;
    if (rb == null) return;

    if (!PayneLabUtils.IsFinite(rb.position) ||
        !PayneLabUtils.IsFinite(rb.velocity) ||
        !PayneLabUtils.IsFinite(rb.angularVelocity))
        return;

    Vector2 rs = _mod.Input.RightStick;

    Vector3 currentLocalAngVel = rb.transform.InverseTransformDirection(rb.angularVelocity);

    if (rs.sqrMagnitude < 0.02f)
    {
        // Gentle damping only when stick is released
        Vector3 dampingTorque = -currentLocalAngVel * 2f;
        dampingTorque = Vector3.ClampMagnitude(dampingTorque, 40f);

        if (dampingTorque.sqrMagnitude > 0.01f)
            rb.AddRelativeTorque(dampingTorque, ForceMode.Acceleration);

        return;
    }

    Vector3 desiredLocalAngVel = new Vector3(
        rs.y * _mod.AerialFlipTorque,
        0f,
        -rs.x * _mod.AerialFlipTorque
    );

    Vector3 error = desiredLocalAngVel - currentLocalAngVel;
    Vector3 localTorque = Vector3.ClampMagnitude(error * AerialTorqueGain, MaxAerialAngularAccel);

    if (localTorque.sqrMagnitude > 0.01f)
    {
        rb.AddRelativeTorque(localTorque, ForceMode.Acceleration);
    }
}
```

This will feel less violent.

# 8. Left/right leg assignment is fragile

`PayneLabLegPoses` uses this:

```csharp
private bool IsLeftJoint(ConfigurableJoint joint, int index)
{
    string n = joint.gameObject.name.ToLower();

    if (n.Contains("left") || n.Contains("lf")) return true;
    if (n.Contains("right") || n.Contains("rt")) return false;

    if (n.EndsWith("l")) return true;
    if (n.EndsWith("r")) return false;

    return index == 0;
}
```

That is dangerous for arbitrary avatars.

If the left/right guess is wrong, asymmetric poses like wall-run, kick, or future directional dive poses can drive the wrong leg.

## Better approach

Since `PayneLabJointControl` already knows the explicit rig bones:

```csharp
rig.m_hipLf
rig.m_hipRt
rig.m_kneeLf
rig.m_kneeRt
```

store those directly.

Example:

```csharp
internal ConfigurableJoint HipLeft;
internal ConfigurableJoint HipRight;
internal ConfigurableJoint KneeLeft;
internal ConfigurableJoint KneeRight;
```

During cache:

```csharp
HipLeft = GetJointOrNull(rig.m_hipLf);
HipRight = GetJointOrNull(rig.m_hipRt);
KneeLeft = GetJointOrNull(rig.m_kneeLf);
KneeRight = GetJointOrNull(rig.m_kneeRt);
```

Then in `PayneLabLegPoses.ApplyPoseToJoints`, prefer direct assignment:

```csharp
if (_mod.JointControl.HipLeft != null)
```

Only fall back to name/array searching if the explicit bones are missing.

This will make left/right behavior much more reliable.

# 10. Friction material replacement may be making legs slippery

In `PayneLabObstacleClearance`:

```csharp
private static PhysicMaterial _slideMaterial;
private static PhysicMaterial _defaultMaterial;
```

And:

```csharp
private static PhysicMaterial GetDefaultMaterial()
{
    if (_defaultMaterial == null)
    {
        _defaultMaterial = new PhysicMaterial("PayneLab_Default");
        _defaultMaterial.hideFlags = HideFlags.HideAndDontSave;
    }

    return _defaultMaterial;
}
```

This creates a new material but does not explicitly set friction values.

Depending on Unity’s default `PhysicMaterial` constructor values, this may not match the original collider friction. If it ends up low/slippery, then after wall-running or sliding, the knee/foot/pelvis colliders may remain on a material that behaves differently from the avatar’s original materials.

That can cause feet/knees to slide weirdly and make the legs look unstable.

## Better approach

Store the original collider materials before changing them, then restore those exact materials.

Conceptually:

```csharp
private readonly Dictionary<Collider, PhysicMaterial> _originalMaterials = new();

private void SetColliderMaterial(Rigidbody rb, PhysicMaterial material, bool rememberOriginal)
{
    if (rb == null || material == null) return;

    try
    {
        var collider = rb.GetComponent<Collider>();
        if (collider == null) return;

        if (rememberOriginal && !_originalMaterials.ContainsKey(collider))
        {
            _originalMaterials[collider] = collider.material;
        }

        collider.material = material;
    }
    catch (System.Exception)
    {
    }
}
```

Then restore:

```csharp
private void RestoreColliderOriginal(Rigidbody rb)
{
    if (rb == null) return;

    try
    {
        var collider = rb.GetComponent<Collider>();
        if (collider == null) return;

        if (_originalMaterials.TryGetValue(collider, out PhysicMaterial original))
        {
            collider.material = original;
            _originalMaterials.Remove(collider);
        }
    }
    catch (System.Exception)
    {
    }
}
```

At minimum, if you keep the shared default material, explicitly set friction:

```csharp
_defaultMaterial.staticFriction = 0.6f;
_defaultMaterial.dynamicFriction = 0.6f;
```

But storing originals is much safer.

```csharp
{
```

Replace `ExecuteDive()` with this safer version:

```csharp
private void ExecuteDive()
{
    var rig = _mod.CachedRig;
    if (rig == null) return;

    CaptureEntryMomentum();

    rig.PhysicalLegs();
    rig.DisableBallLoco();

    Vector3 headFwd = GetFacingDirection();
    Vector3 headRight = Vector3.Cross(Vector3.up, headFwd).normalized;

    Vector2 ls = _mod.Input.LeftStick;

    Vector3 horizontalDir = headFwd;

    if (ls.sqrMagnitude > 0.1f)
    {
        horizontalDir = (headFwd * ls.y + headRight * ls.x).normalized;
    }

    if (horizontalDir.sqrMagnitude < 0.001f)
        horizontalDir = headFwd;

    horizontalDir.Normalize();

    var rb = _mod.CachedPelvisRb;

    if (rb != null && PayneLabUtils.IsFinite(rb.velocity))
    {
        Vector3 currentVel = rb.velocity;
        Vector3 currentFlat = new Vector3(currentVel.x, 0f, currentVel.z);

        float currentSpeed = currentFlat.magnitude;
        float entrySpeed = new Vector2(_entryVelocity.x, _entryVelocity.z).magnitude;

        // DiveImpulseForce now behaves like target horizontal speed in m/s.
        float diveSpeed = Mathf.Clamp(_mod.DiveImpulseForce, 1f, 20f);

        float desiredSpeed = Mathf.Max(currentSpeed, entrySpeed, diveSpeed);

        Vector3 desiredVel = horizontalDir * desiredSpeed;

        // Small upward pop, but not enough to slam the solver.
        desiredVel.y = Mathf.Max(
            currentVel.y,
            Mathf.Min(2.5f, desiredSpeed * 0.15f)
        );

        Vector3 delta = desiredVel - currentVel;

        if (PayneLabUtils.IsFinite(delta))
        {
            // Prevent absurd single-frame velocity changes.
            delta = Vector3.ClampMagnitude(delta, 12f);
            rb.AddForce(delta, ForceMode.VelocityChange);
        }
    }

    _mod.ActiveInput = InputMode.ProcLeg;
    _mod.SetState(StuntState.DiveProne);

    _actionLockTimer = 0.6f;
    _diveAirborneLock = 0.35f;

    _groundedVelTimer = 0f;
```

```csharp
private void ApplyAerialTorque()
{
    var rb = _mod.CachedPelvisRb;
    if (rb == null) return;

    if (!PayneLabUtils.IsFinite(rb.position) ||
        !PayneLabUtils.IsFinite(rb.velocity) ||
        !PayneLabUtils.IsFinite(rb.angularVelocity))
    {
        return;
    }

    Vector2 rs = _mod.Input.RightStick;

    Vector3 currentLocalAngVel =
        rb.transform.InverseTransformDirection(rb.angularVelocity);

    if (rs.sqrMagnitude < 0.02f)
    {
        // Gentle damping only when stick is released.
        Vector3 dampingTorque = -currentLocalAngVel * 2f;
        dampingTorque = Vector3.ClampMagnitude(dampingTorque, 40f);

        if (dampingTorque.sqrMagnitude > 0.01f)
            rb.AddRelativeTorque(dampingTorque, ForceMode.Acceleration);

        return;
    }

    Vector3 desiredLocalAngVel = new Vector3(
        rs.y * _mod.AerialFlipTorque,
        0f,
        -rs.x * _mod.AerialFlipTorque
    );

    Vector3 error = desiredLocalAngVel - currentLocalAngVel;

    Vector3 localTorque = Vector3.ClampMagnitude(
        error * AerialTorqueGain,
        MaxAerialAngularAccel
    );

    if (localTorque.sqrMagnitude > 0.01f)
    {
        rb.AddRelativeTorque(localTorque, ForceMode.Acceleration);
    }
}
```

This prevents the right stick from becoming a hard angular brake when released.

## F. Add diagnostic bypass for joint target conversion

Replace `ComputeJointTargetRotation()` with:

```csharp
private Quaternion ComputeJointTargetRotation(ConfigurableJoint joint, Quaternion desiredPose)
{
    if (joint == null) return Quaternion.identity;

    if (!IsValidQuaternion(desiredPose))
        desiredPose = Quaternion.identity;

    // Diagnostic mode:
    // If this calms the legs, the joint-space conversion below is the main issue.
    if (_mod.DebugSimpleJointTargets)
    {
        return Quaternion.Inverse(desiredPose);
    }

    Quaternion inv = Quaternion.Inverse(desiredPose);

    Vector3 right = joint.axis;
    Vector3 forward = Vector3.Cross(joint.axis, joint.secondaryAxis);

    if (forward.sqrMagnitude < 0.0001f)
    {
        return inv;
    }

    forward.Normalize();

    Vector3 up = Vector3.Cross(forward, right).normalized;
    Quaternion jointSpace = Quaternion.LookRotation(forward, up);

    return Quaternion.Inverse(jointSpace) * inv * jointSpace;
}
```

Test this toggle:

- If legs calm down with `Debug Simple Joint Targets = true`, the old conversion is avatar-axis-dependent and wrong for that rig.
- If legs get worse, set it back to false.

Long term, we should replace this with per-joint calibration instead of a generic axis conversion.

```csharp
{
    if (_mod.CurrentState != StuntState.SideLying &&
        _mod.CurrentState != StuntState.DiveProne)
    {
        return;
    }

    // Do not fight active right-stick orientation input.
```

# 9. About omnidirectional diving/proning with RS

Do not build full RS omnidirectional prone control until the legs are stable.

The current RS torque is angular-velocity-based and only controls pitch/roll, not yaw. For proper omnidirectional prone/diving, you eventually want a separate controller that does this:

- RS direction defines desired body heading relative to camera/head.
- Apply PD torque around world-up for yaw.
- Apply limited pitch torque only when not pressed into the floor.
- Do **not** make knee targets react to the resulting angular velocity.
- Keep prone leg targets very soft and mostly passive.

But first, stabilize the legs with the patch set above.

The biggest immediate red flags from the full file set are the friction restore issue, the overly permissive grounded contact check, the huge dive impulse, and the joint target conversion.
